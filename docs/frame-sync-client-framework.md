## 1. 【代码现状】客户端帧同步：服务器权威中继锁步（Relay-Lockstep）

### 1.1 一句话概括

客户端**不预测、不回滚、不跑在服务器前面**。它每逻辑帧（20Hz）采集一次输入 → 发给服务器 → **等服务器把本帧的帧命令（`FRAME_NTF`）广播回来** → 才推进本地模拟。也就是说客户端模拟严格「落后并跟随」服务器帧，中间隔着约一个网络往返（RTT）的固定延迟。

### 1.2 逻辑帧率与时钟

- **20Hz 固定步长**，`50ms/帧`。
- 时钟定义在 `shared/battlecore/BattleClock.h`：`kLogicFps = 20`、`kFixedDeltaMs = 50`。
- `StageScene::update` 里用**固定步长累加器**驱动：每帧渲染回调里累加真实 dt，`while (累加 ≥ 50ms)` 才推进一个逻辑帧（采样输入 + 推进模拟）。渲染帧率与逻辑帧率解耦，逻辑严格 20Hz。

### 1.3 输入采样 → 上报

- `StageScene::sampleNetInput()`：从 HUD 的方向角（弧度）用 `DirFromRadians` 量化成 8 方向 `move_dir`，射击方向用 `shoot_dx/shoot_dy`（连续方向向量, Q16.16 定点）直接上报；另有 `AutoTestConfig` 自动测试输入。
- `UINetBattleLayer::onInputSampled` → 发 `EInputReq`（`BATTLE_INPUT_REQ`），带 `client_frame` 和 `PlayerInput{move_dir, shoot_dx, shoot_dy, skill_id, fire, gun_type}`。
- 输入契约 `battlecore::PlayerInput`（移动 8 方向 0-8 + 射击连续向量 shoot_dx/shoot_dy + fire/skill/gun_type）是客户端↔服务器共享的，`shared/battlecore/BattleInput.h` 定义。

### 1.4 服务器中继 → 帧命令广播

- 服务器（`BattleActor`）收到各客户端本帧输入后，把全员输入打包成 **`BATTLE_FRAME_NTF{frame_id, inputs[]}`** 广播给全员。
- 注意：这里是**中继**——服务器把「这一帧每个玩家输入是什么」原样广播（权威模拟的服务器侧落地是另一个话题，见 §7.6 的定点核心），客户端据此重放。

### 1.5 客户端收帧 → 按序补帧重放

- `UINetBattleLayer::onFrameNtf` → `StageScene::onNetFrame`：把收到的 `FRAME_NTF` 按 `frame_id` 缓冲到队列 `m_netFrameInputs`。
- `StageScene::drainNetFrames`：每逻辑帧从队列里按 `frame_id` 顺序取帧 → `doNetSimFrame`。
- `doNetSimFrame`：把该帧全员输入写回各英雄 → 调 `do_GameRunning`（推进一帧真实战斗：英雄→HUD→技能→开火→武器→小怪→视角）→ 每 50 帧打一条稀疏同步日志。

### 1.6 确定性 RNG

- `shared/battlecore/BattleDeterminism.h`：`NetRandom/NetRandomRange/NetFrandom01/...`——联网模式走确定性 PRNG（`CBattleRng`，splitmix64），单机走 `rand()`/墙钟。
- `Defines.h` 把游戏内的 `random(n)`/`CCRANDOM_0_1()`/`frandom` 重定向到 `NetXxx`；`Tools::millisecondNow` 联网走逻辑帧时钟。
- `seed` 由服务器在 `BATTLE_ENTER_RSP` 里下发，客户端用它初始化本地 PRNG。

### 1.7 现状的已知问题（你点名「还有很多问题」）

基于代码现状，列出我核实到的问题点（分类：正确性 / 延迟 / 健壮性）：

| # | 问题 | 类别 | 说明 |
|---|---|---|---|
| A1 | **客户端不预测，纯等待服务器帧** | 延迟 | 每帧动作要等一个 RTT 才生效；RTT 100ms 时手感约 150–200ms 延迟，明显「飘」。守望先锋用预测+和解解决，见 §2。 |
| A2 | **没有回滚/和解机制** | 正确性 | 一旦本地与服务器状态漂移，没有 checkpoint/rollback 纠正，只能靠「稀疏 sync 日志」人工比对，发现不一致也纠正不了。 |
| A3 | **补帧策略是「等帧」，没有插值/缓冲深度控制** | 延迟/抖动 | 网络抖动时 `drainNetFrames` 要么空转要么积压，没有 jitter buffer、没有时间膨胀，卡顿直接反映到逻辑。 |
| A4 | **一致性校验是「日志级别」而非「协议级别」** | 正确性 | 设计文档 §7.3 写了 `BATTLE_HASH_NTF` 哈希比对 + 失配回发快照，但客户端代码里只有每 50 帧一条日志，没有真正上报哈希、没有快照和解链路。 |
| A5 | **输入与帧号的对应关系脆弱** | 正确性 | `client_frame` 由客户端自己标，服务器以谁的帧号为准？跨端时钟未严格定义，容易出现帧号错位。 |
| A6 | **重连/快照是「设计有、代码无」** | 健壮性 | `ESnapshotNtf` 有注册 handler，但完整断线重连→快照对齐→增量播放的闭环没跑通。 |
| A7 | **单机与联网两套驱动并存** | 架构 | `update` 里联网走「采样+等帧」，单机走 `do_GameRunning` 直接跑；两套 tick 入口易漂移，且 R6（可变 dt vs 固定步长）语义不一致。 |

> 这些是「问题清单」，不是「我改完了」。改造方案在 §4。

## 2. 【守望先锋事实】Overwatch 客户端帧同步设计

来源：Tim Ford（Blizzard，首席玩法程序）GDC 2017《Overwatch Gameplay Architecture and Netcode》演讲 + 后续公开技术讨论。下面是该演讲里与「客户端帧同步」直接相关的、可核对的要点。

### 2.1 总体模型：服务器权威 + 客户端预测 + 回滚和解

- **服务器权威**：服务器跑一份完整、确定性的权威模拟（ECS），是唯一真相源。
- **客户端预测（prediction）**：客户端也跑同一份模拟，且**跑在服务器前面**——本地输入**立即生效**（不等服务器），本地先演出来。
- **回滚与和解（rollback & reconciliation）**：客户端持续缓存自己的历史快照（checkpoint）。当收到服务器「真正确认」的帧命令时，如果和本地预测结果不一致，就**回滚到最近一次一致快照 + 按服务器命令重放**，纠正偏差。

### 2.2 指令帧（command frame）与帧率

- 指令帧是固定的：默认 **16ms（60Hz）**，竞技/高刷新模式 **7ms（128Hz/144Hz）**。
- 客户端每指令帧打包一次输入命令发给服务器（UDP，带冗余重发，见 §2.6），命令里带目标帧号，而不是只发「当前输入」。

### 2.3 客户端超前量（run-ahead）

- 客户端不是无限超前，而是**超前约半个 RTT + 一小段缓冲**（把服务器帧到本地的时间差补回来），这样本地手感即时、同时服务器帧追上来时有时间做和解。
- 这个「超前量」是动态计算的，是延迟补偿的核心参数。

### 2.4 网络延迟补偿：favor-the-shooter（偏向射击方）

- 这是服务器端做的**回溯校验（lag compensation）**：服务器在判定「A 打没打中 B」时，不是看 B 当前位置，而是**回看 B 在 A 扣扳机那个时刻的历史位置**（服务器同样保留历史快照），据此判定命中。
- 目的：让「我看到我打中了他」成立，牺牲一点点「被打方的真实位置」，这是 Overwatch 手感的关键，也是它「服务器权威」模型下仍能很跟手的原因。

### 2.5 ECS 与「网络只加 3 个系统」

- Overwatch 用 ECS（Entity-Component-System）。演讲里有个著名说法：**确定性模拟 + ECS 之后，网络层只剩 3 个系统**——(1) 预测系统（客户端本地推进）、(2) 和解系统（回滚）、(3) 快照系统（历史状态缓存）。其余玩法系统完全感知不到自己在「联网」还是「单机」。

### 2.6 传输细节

- **UDP**，不是 TCP。自定义可靠性：**指令冗余重发**（同一条命令连续发多帧，丢一个也有下一个兜底），不做 TCP 式重传等待。
- **时间膨胀（time dilation）**：网络拥塞时，不是掉帧，而是让逻辑帧率**临时变慢**（拉伸时间），给网络腾出追帧空间，避免硬卡。

### 2.7 与我方案可借鉴 vs 不可照搬的区分

- **可借鉴**：预测+和解的骨架、超前量计算、favor-the-shooter、UDP 冗余、时间膨胀、ECS 把网络隔离成 3 个系统的思想。
- **不可照搬**：守望是 6v6 FPS、60/128Hz、UDP 直连、超大规模 ECS；我们是 20Hz、2 人（或小规模）联机、走 gRPC/既有连接、Cocos 实体非 ECS。**帧率、传输、实体架构都要按我们的规模降级适配**，照抄参数是错的。

## 3. 【差距】现状 vs 守望先锋

| 维度 | 现状（§1） | 守望先锋（§2） | 差距定位 |
|---|---|---|---|
| 模型 | 服务器权威**中继锁步** | 服务器权威 + **预测+和解** | 核心差距：无预测、无和解 |
| 客户端运行位置 | **落后**服务器约 1 RTT | **超前**服务器约 0.5 RTT | 手感差距 |
| 输入生效 | 等服务器帧回来才动 | 本地**立即**生效 | 延迟差距 |
| 漂移纠正 | 无（只有日志） | checkpoint 回滚重放 | 正确性差距 |
| 帧率 | 20Hz 固定 | 16ms/7ms 固定 | 规模差距（可接受） |
| 延迟补偿 | 无 | favor-the-shooter 回溯 | 命中公平性差距 |
| 传输 | 既有连接（gRPC/Relay） | UDP 冗余 | 架构差距（短期可不改） |
| 抖动处理 | 无 | jitter buffer + 时间膨胀 | 体验差距 |

**结论**：要「像守望先锋一样跟手」，最值得做、收益最大的一件事是 **A（客户端预测 + 回滚和解）**，其次是 **B（超前量/jitter buffer + 时间膨胀）**。favor-the-shooter 和 UDP 是更高阶的，可放后续。

## 4. 【改造提案】客户端帧同步改造（供评审，未实现）

> 这一整节都是我的提案，**需要你逐条确认**，不是已完成的代码。

### 4.1 目标模型（降级版守望先锋）

**服务器权威 + 客户端预测 + 回滚和解**，参数按 20Hz / 2 人规模降级：

```
客户端本地：
  每逻辑帧：
    1. 采样输入，打上 target_frame 号，发给服务器（冗余：连续发 2 帧）
    2. 本地立即把输入喂给「本地预测核心」，推进一帧 → 立刻渲染（即时手感）
    3. 本地核心每个 checkpoint 间隔存一份快照（如每 10 帧）
    4. 收到服务器 FRAME_NTF{frame_id, inputs[]}：
        a. 若 frame_id 对应的本地预测结果 == 服务器命令 → 丢弃/确认
        b. 若不一致 → 回滚到最近一个 ≤ frame_id 的快照 → 按服务器 inputs 重放到 frame_id
    5. 渲染层在「预测帧」与「已确认帧」之间做插值，抹平回滚跳变
```

### 4.2 需要的核心能力（映射到现有代码）

| 能力 | 现状 | 改造 |
|---|---|---|
| 本地预测核心 | `do_GameRunning` 直接改实体 | 换成 `CBattleCore`（共享定点核心）跑本地预测，`StageScene` 只读核心状态渲染（这同时是浮点→定点改造 P3 的目标，两件事合流） |
| 快照/回滚 | 无 | `CBattleCore::SerializeState/DeserializeState` 已具备，补一个 checkpoint 环形缓冲 |
| 帧命令对齐 | `drainNetFrames` 顺序消费 | 改成「按 frame_id 索引对齐 + 追帧/回滚」 |
| 哈希校验 | 日志 | 落地 `BATTLE_HASH_NTF` 上报 + 失配回发 `BATTLE_SNAPSHOT_NTF`（设计文档 §7.3 已有协议，补实现） |
| 超前量/jitter buffer | 无 | 客户端维护输入队列 + 目标缓冲深度，按 RTT 动态调超前量 |

### 4.3 分阶段（每阶段可冒烟、可回退）

- **F0**：把 §1 现状文档固化为基线（本文即 F0 产出）。
- **F1**：客户端预测——本地 `CBattleCore` 立即消费输入渲染，不等服务器帧（**不破坏现状**，先用开关隔离）。
- **F2**：回滚和解——checkpoint + 收到 `FRAME_NTF` 后 diff/回滚重放。
- **F3**：哈希校验闭环——`BATTLE_HASH_NTF` + `BATTLE_SNAPSHOT_NTF` 自动纠偏。
- **F4**：jitter buffer + 超前量 + 时间膨胀（可选，体验项）。
- **F5**：favor-the-shooter / UDP 冗余（可选，高阶项）。

> 优先级建议：F1/F2/F3 是「正确性 + 手感」刚需；F4 是体验优化；F5 视规模再定。**F1 依赖浮点→定点核心移植（P2/P3）先落地**，因为「本地预测核心」必须和「服务器权威核心」是同一份代码，否则预测永远对不上。

## 5. 【自动评测】冒烟测试 → 修复 → 自动进入下一核心改动

按你「几大核心改动都需要冒烟测试修复，然后自动进入下一个核心功能改动」的要求，本文与后续改造统一走这套自动评测环：

### 5.1 评测环（每个核心改动都套用）

```
[改代码] → [单测(位一致/哈希一致)] → [冒烟测试(双端联机)] → [自动判错] → [修复] → [再测] → [绿] → [自动进入下一改动]
```

### 5.2 分层评测

| 层 | 手段 | 判据 | 触发 |
|---|---|---|---|
| **L1 单元** | MSVC 单测 exe（如 `test_sp01move.exe`） | 同种子同输入 → 同 `HashState`；单测退出码 0 | 每次改核心后 |
| **L2 确定性** | 客户端/服务器各跑 `HashState`，diff 哈希 | 逐位一致 | 联机前 |
| **L3 冒烟** | `smoke_test.ps1` 起两客户端联机 | `sog_flow.log` 两端 `sync frame=N` 一致；无 `sog_crash.log` | 每个里程碑 |
| **L4 回归** | 录制输入重放，旧 vs 新 diff 位置/HP/子弹数 | 无差异或差异全在「有意差异清单」 | P5 / F 收尾 |

### 5.3 「自动进入下一改动」的落地方式

- 每个核心改动写一个**验收脚本**（脚本里把 L1 单测 + L3 冒烟串起来），脚本返回 0 才算「绿」。
- 绿了之后**不人工确认**，直接按 §4.3 / P0–P5 的顺序进入下一项；红了才停下找我修。
- 冒烟测试脚本已存在：`EnvRoot/smoke_test.ps1`（起两客户端联机、抓崩溃栈、退出码 0/2/3/4 语义已定义），复用即可。
