# 游戏配置文件体系 —— Excel → bin + 运行时读取 + Redis 热更框架

> 版本：v1（2026-09-15）
> 标注约定同 `frame-sync-client-framework.md`：【代码现状】【改造提案】【事实】。
> 本文是**设计提案**（尚未实现），目标：客户端与服务器共用一份游戏内数据，数据不进代码、不进帧同步内核。

---

## 0. 目标与边界

### 0.1 目标

1. **类型定义 + 实体数据** 写进 Excel，打包成 **bin** 文件给客户端（服务器）使用。
2. **帧同步内核 + 游戏框架** 只做「读取后的运算 + 实体实例化」，其余数据（属性/速度/血量/掉落/波次/技能/碰撞盒参数…）全部来自配置文件。
3. 方便后续**游戏内容新增/修改**（策划改 Excel → 重新打包 → 生效，无需改代码）。
4. **配置热更框架**：服务器用 **Redis 发布/订阅** 推送变更通知，客户端通过连接**动态拉取**热更。

### 0.2 边界（明确不做什么）

- 不把「逻辑」写进配置（配置只有数据，没有表达式/脚本；需要逻辑的地方留 `skill_id`/`ai_type` 等枚举，逻辑仍落 C++/Lua）。
- 不做 Excel 在线编辑/协作（用本地 Excel + 导出工具）。
- 帧同步内核**不直接读 Excel/不读 JSON**，只读内存里的已解析结构（`CConfigTable<T>`）。

## 1. 总体架构

```
[策划 Excel 表]
   │  (1) 导出工具 export_config (C++/Python，本地或 CI)
   ▼
[bin 文件]  magic + 版本 + 表结构(schema) + 行数据 + 字符串表 + 索引 + 校验
   │  (2) 上传/分发 (文件服务器 或 版本仓库)
   ▼
[服务器] 启动/热更时加载 → CConfigMgr 解析成内存表 → 通过 Redis pub/sub 发布「配置版本变更」
   │
   │  (3) Redis channel: "config:changed" { version, table, url, hash }
   ▼
[客户端] 连接上监听变更 → 版本比对 → 动态拉取新 bin → 校验 → 原子替换 → 重新实例化受影响实体
```

关键原则：**bin 是唯一分发物**，Excel 只是编辑源；运行时（客户端+服务器）只认 bin，不认 Excel。

## 2. 【改造提案】bin 文件格式

### 2.1 设计目标

- **版本化 + 校验**：任何字节变化都会改变版本哈希，客户端能判断「我是不是最新」。
- **按表 / 按行随机访问**：运行时不必全量解析，按 `(表名, 主键 id)` O(1) 取行。
- **整数友好**：帧同步内核要定点化，配置里数值尽量用**整数缩放**存储（如伤害 `×100`、速度 `px/s`），避免浮点字面量跨平台解析差异（与 `multiplayer-design.md` R7 呼应）。
- **字符串共享**：所有字符串进一个字符串表，行内只存偏移，省空间 + 便于 diff。

### 2.2 布局（草案）

```
+---------------------------------------------------------------+
| Header                                                         |
|   magic: "RSCFG" (0x52 0x53 0x43 0x46 0x47)                    |
|   bin_version: uint32        (格式版本，加字段就 +1)            |
|   content_hash: uint64       (内容 FNV-1a，用于热更比对)        |
|   table_count: uint32                                          |
|   schema_hash: uint64        (表结构校验，防 schema 与数据错配) |
+---------------------------------------------------------------+
| Table Directory (table_count 项)                               |
|   每个: { table_name_offset, row_count, row_offset,            |
|           schema_offset }                                       |
+---------------------------------------------------------------+
| Schema Section (每表一份)                                       |
|   字段描述: { field_name, type(1字节枚举), default }            |
|   type: i32/i64/fx(fx_t)/f32/str/bool/enum(uint8)/array        |
+---------------------------------------------------------------+
| Data Section (每表行数据)                                       |
|   行: { id(uint32), 各字段值(按 schema 顺序定长/变长) }          |
+---------------------------------------------------------------+
| String Table (去重后的所有字符串)                               |
+---------------------------------------------------------------+
| Index Section (每表: id → 行偏移 的有序数组, 二分查找)           |
+---------------------------------------------------------------+
| Footer: content_hash 回写 + 长度 + 简单校验(可选 CRC32)         |
+---------------------------------------------------------------+
```

### 2.3 字段类型与定点口径

| 类型 | 存储 | 说明 |
|---|---|---|
| `i32/i64` | 定长 | 整数，HP/数量/帧数/枚举 id |
| `fx` | `int32`（Q16.16 原始位） | 速度/距离/伤害系数等。**Excel 里写浮点**，导出时 `FxFromFloat` 一次性转成定点位存进 bin，运行时零转换 |
| `f32` | `float` | 仅限**非逻辑**表现参数（特效缩放、音效音量），不进帧同步内核 |
| `str` | 偏移进字符串表 | 名字/描述/资源路径 |
| `bool` | `uint8` | 0/1 |
| `enum` | `uint8/uint16` | 动作/状态/classId 等，导出时按 schema 校验枚举合法性 |
| `array` | 长度 + 元素 | 掉落表、波次表等变长数据 |

> **红线**：凡是会被帧同步内核消费的数值，一律 `fx` 或整数，**禁止 `f32`**。这样「配置 → 内核」全程定点，无跨平台漂移。

## 3. Excel 表组织（策划视角）

### 3.1 表与 Sheet 的约定

- 每个 Excel 文件 = 一类实体/系统（如 `hero.xlsx`、`sp01.xlsx`、`bullet.xlsx`、`skill.xlsx`、`wave.xlsx`、`prop.xlsx`）。
- 每个 Sheet = 一张表；Sheet 名 = 表名（运行时 `GetTable("Sp01Info")` 用）。
- **第一行 = 字段名**；**第二行 = 类型标注**（`i32`/`fx`/`str`/…）；**第三行 = 注释**；第四行起 = 数据。
- 第一列固定为 `id`（主键，全表唯一，热更/索引/引用都靠它）。

### 3.2 示例：`sp01.xlsx` 的 `Sp01Info` sheet

| id | name | classId | maxHp | walkSpeed(fx) | hurtToHero | dropTable(array) |
|----|------|---------|-------|---------------|------------|------------------|
| 1  | 僵尸 | 0       | 100   | 5.0           | 1          | [1001,1002]      |
| 2  | 守卫 | 10      | 300   | 3.5           | 3          | [1003]           |

- `walkSpeed` 存 `fx`：Excel 写 `5.0`，导出成 `5.0<<16`，内核读出来直接参与定点运算。
- `dropTable` 存 `array`：引用 `prop.xlsx` 里的 id。

### 3.3 类型定义（schema）也进 bin

- 你说的「将类型定义和实体数据写入 Excel」：**类型定义 = 每张表第二行的字段类型标注**，导出工具据此生成 schema（§2.2 Schema Section）。
- 好处：客户端/服务器读 bin 时**用同一份 schema 校验**，字段错位/类型错配在加载期就报错，而不是运行期崩。

## 4. 导出工具（Excel → bin）

### 4.1 实现选型

- **首选 C++（复用现有 `tools/` 或新增 `tools/config_exporter/`）**，理由：
  - 和服务器同栈，`FxFromFloat` 等定点转换直接复用 `shared/battlecore/FixedPoint.h`，保证「导出时的浮点→定点」与「运行时」是**同一份代码**（消除转换口径差异）。
  - 无 Python 依赖，CI/服务器环境一致。
- 备选 Python（`openpyxl`/`xlrd`），仅用于快速原型；正式走 C++ 以免浮点转换两套实现。

### 4.2 导出流程

1. 读 Excel（`.xlsx` 本质是 zip + xml，用第三方库如 `libxlsxwriter` 的读取侧 / `pugixml` 解 zip 自解析）。
2. 按 Sheet 名 + 第二行类型标注生成 schema。
3. 逐行校验：类型合法、`id` 唯一、`enum` 值在枚举表内、`fx` 数值可表示、`array` 引用 id 存在。
4. 数值转换：`fx` 字段 `FxFromFloat`；`f32` 保留；字符串入字符串表。
5. 序列化成 §2.2 布局，算 `content_hash`，落盘 `xxx.bin` + 生成一份 `xxx.bin.json`（人类可读，用于排查）。
6. 输出**清单**：`{表名, 版本哈希, 行数, 文件大小}`，供热更推送用。

### 4.3 一致性保障

- 同一次导出，`content_hash` 唯一标识内容；内容不变则 hash 不变（幂等，CI 可据此跳过分发）。
- schema 与数据错配 → 导出直接报错，不产出 bin（避免坏包上线）。

## 5. 运行时读取（共享 `CConfigMgr`）

### 5.1 分层

| 层 | 位置 | 职责 |
|---|---|---|
| `shared/config/`（**客户端/服务器共用**） | `CBinReader` / `CConfigTable<T>` | 纯解析：读 bin → 内存表，`Get(id)` 随机访问。**无引擎依赖，无 Redis/网络** |
| 服务器 `engine/xConfig/` | `CConfigMgr` | 管理多表、版本、热更加载、发 Redis pub/sub |
| 客户端 `Config/` | `CClientConfigMgr` | 加载本地 bin、监听热更、原子替换 |

### 5.2 `CConfigTable<T>` 访问契约（帧同步内核只碰这个）

```cpp
// 内核/游戏框架只做「读取后的运算 + 实例化」，数据从配置来：
const Sp01Info& info = config.GetTable<Sp01Info>().Get(id);   // O(1)，按 id 二分
sp01.maxHp   = info.maxHp;      // 已经是 int
sp01.walkSpeed = info.walkSpeed; // 已经是 fx_t
sp01.dropTable = info.dropTable; // std::vector<int32>
```

- `Sp01Info` 是**生成的结构体**（导出工具同时生成一份 C++ 头，字段与 schema 严格对齐），这样内核读配置是**强类型 + 编译期校验**，不是靠字符串 key 反射。
- 生成头由导出工具产出（`source/config-gen/Sp01Info.h` 之类），**生成物不进 git 手改**（对齐 `proto-cpp` 的约定）。

### 5.3 实例化边界

- **帧同步内核**：只在 `Init` / spawn 时调 `Get(id)` 把配置值拷进 `HeroState/Sp01State/...` 的字段，之后 tick 内**不再碰配置**（避免每次读配置引入非确定性或开销）。
- **游戏框架**：负责「何时实例化哪个 id 的实体」的编排（波次刷怪、掉落），实例化参数来自配置。
- 这样「内核=纯运算 + 实例化」，和你的要求一致。

## 6. 【改造提案】配置热更框架（Redis pub/sub + 客户端拉取）

### 6.1 推送：服务器 Redis 发布/订阅

- 服务器 `CConfigMgr` 在**加载到新版本配置**后，向 Redis 频道发布变更通知：

```
PUBLISH config:changed   '{"version": 7, "contentHash": "a3f2...", "tables": ["Sp01Info","SkillInfo"], "url": "http://cfg/res/7/", "size": 123456}'
```

- 通知字段：`version`（单调递增）、`contentHash`、`tables`（本次变了哪些表）、`url`（下载地址/前缀）、`size`。
- **为什么 Redis pub/sub**：服务器是多进程集群（Gate/Login/Game 等），Redis 是现成的跨进程广播总线；配置更新只需「发布一次」，各进程订阅同一 channel 即知。**Redis 是通知通道，不是配置数据本身**（配置数据走文件下载，避免把大 bin 塞进 Redis）。

### 6.2 拉取：客户端通过连接动态拉取

客户端不直接连 Redis（客户端在玩家机器上，不应碰服务器 Redis），而是：

```
[服务器进程] 收到 Redis config:changed
      │  通过既有的「客户端↔服务器」连接下发一个轻量通知
      ▼
[客户端]  收到 ConfigChangedNtf{version, contentHash, url}
      │  比较本地 version < 服务器 version？
      ▼ 是
[客户端]  通过 url 拉取新 bin（全量 或 diff 补丁）→ 校验 contentHash 与 size
      ▼ 校验通过
[客户端]  原子替换本地配置 + 重新实例化受影响实体
      ▼
[客户端]  上报 ConfigAck{version}，服务器确认客户端已同步
```

- **通知下发通道**：复用现有协议（新增 `CONFIG_CHANGED_NTF` / `CONFIG_PULL_REQ/RSP` 或走既有 `AT_*` big_type），**不新开长连接**。服务器订阅 Redis channel → 收到变更 → 翻译成客户端协议下发。
- **拉取 URL**：由 `CConfigMgr` 生成，指向配置文件服务（可以是内网 HTTP/文件服务器，或直接把 bin 走现有 RPC 分块传输）。大文件分块拉 + 断点续传 + 拉完整体 hash 校验。

### 6.3 原子替换与回滚

- 客户端「新 bin 下载完整 + hash 校验通过」后，才**原子替换**（先写临时文件 → `rename`/指针切换）。
- **受影响实体重实例化**：按通知里的 `tables` 判断——若只改了 `SkillInfo`，就不重刷怪物；若改了 `Sp01Info`，则对场上的怪物按新配置重算属性（或等待下一波刷怪生效）。**帧同步战斗进行中不做热更实体替换**（避免确定性被破坏），热更只在「无战斗 / 房间外 / 下一局开始」落地；战斗内只做「标记，下一局生效」。这是热更与帧同步确定性冲突的关键边界，见 §7 风险 R-C2。
- **回滚**：客户端保留上一版本 bin；新版本校验失败或运行时异常 → 回退旧版本并上报。

### 6.4 服务器侧热更落地时机

- 服务器加载新配置同样要**避开正在跑的战斗局**：新配置只对**新建的局**生效，已开局继续用旧配置跑完（确定性要求：一局中途配置不能变）。
- 这样「配置热更」对**在线玩家的正在进行的战斗**是零侵入的。

## 7. 风险点

| # | 风险 | 缓解 |
|---|---|---|
| R-C1 | **Excel 里的浮点字面量跨平台解析差异** | 数值字段统一 `fx`/整数，导出时 `FxFromFloat` 用**同一份 C++ 代码**（§4.1），客户端/服务器共享；禁用 `f32` 进内核 |
| R-C2 | **热更与帧同步确定性冲突**（战斗中途换配置 → 状态漂移） | 热更只对「下一局 / 无战斗」生效；战斗中只标记不替换（§6.3/§6.4） |
| R-C3 | **schema 与数据错配** | 导出期校验 + 运行时 schema_hash 比对，错配拒载 |
| R-C4 | **bin 大 / 拉取慢** | 字符串去重 + 分块拉 + 断点续传 + 未来做 diff 补丁（只拉变动的表） |
| R-C5 | **字段增删导致旧客户端 bin 不兼容** | `bin_version` 递增 + 客户端拉新前校验版本；格式兼容性由导出工具保证 |
| R-C6 | **生成代码/生成物管理** | 生成头 `config-gen/`、bin 都作为生成物，进 `.gitignore`/CI 产物仓库，不手改（对齐 `proto-cpp` 约定） |
| R-C7 | **配置引用完整性**（dropTable 引用不存在的 id） | 导出期全表引用校验，缺失即报错 |

## 8. 分阶段执行

| 阶段 | 内容 | 验收 |
|---|---|---|
| **C0** | 定 bin 格式 + 一个最小表（`Sp01Info`）Excel 样板 + schema 定义 | 格式文档 + 样例表评审通过 |
| **C1** | 导出工具 v1：读 Excel → 校验 → 生成 bin + 生成 C++ 结构体头 | 能导出样例表，bin 可读、生成头可编译 |
| **C2** | `shared/config/` 读取器 `CBinReader`/`CConfigTable<T>` | 单测：随机访问、类型校验、hash 校验、坏包拒载 |
| **C3** | 服务器 `CConfigMgr` 加载 + Redis pub/sub 发布 | 加载样例 bin，发布变更，订阅端收到 |
| **C4** | 客户端拉取：协议通知 + 分块下载 + 原子替换 + 回滚 | 模拟服务器推新版本，客户端拉到并替换 |
| **C5** | 与帧同步内核打通：实例化改从配置读，内核不再硬编码数值 | 刷怪/属性从 bin 来，内核零硬编码 |
| **C6** | 热更完整闭环 + 战斗隔离（下一局生效） | 推新配置，旧局不变，新局用新配置 |

依赖：C0→C1→C2→C3→C4 串行；C5 依赖 C2；C6 依赖 C3+C4+C5。

## 9. 【自动评测】配置体系的冒烟测试环

沿用 `frame-sync-client-framework.md` §5 的分层评测，配置体系增加专属判据：

| 层 | 手段 | 判据 |
|---|---|---|
| **C-L1 导出** | 导出工具跑样例 Excel | 退出码 0；产出 bin + 生成头；hash 幂等（同输入两次导出同 hash） |
| **C-L2 读取** | `CBinReader` 单测 | 随机访问正确；类型/schema/hash 校验生效；坏包拒载 |
| **C-L3 热更** | 单机模拟服务器推新版本 | 客户端版本号单调递增；hash 校验失败时回滚到旧版；原子替换无半包 |
| **C-L4 联机** | `smoke_test.ps1` + 推一次配置热更 | 旧局跑完不漂移；新局用新配置；两端 `sync frame=N` 一致；无 `sog_crash.log` |

绿了自动进入下一阶段（§8），红了停下修复——与你「冒烟测试修复 → 自动进入下一核心功能改动」一致。
